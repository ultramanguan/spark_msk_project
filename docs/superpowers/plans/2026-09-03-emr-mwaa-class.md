def nb(cells):
    return {
        "cells": cells,
        "metadata": {"kernelspec": {"display_name": "PySpark", "language": "python", "name": "pysparkkernel"}},

    return {"cell_type": "code", "id": uuid.uuid4().hex[:8], "execution_count": None, "metadata": {}, "outputs": [], "source": text.splitlines(keepends=True)}

md("# Class 1 — Spark Batch Processing (EMR)\n\nThis notebook explains **how Apache Spark executes batch jobs**, from the programming model down to the physical execution engine. It is meant to be read top to bottom, then run cell by cell.\n\n## 1. What problem Spark solves\n\nA single machine cannot hold or process a dataset that is terabytes in size in reasonable time. Spark solves this by:\n\n- **Partitioning** data across many machines (executors).\n- Describing computation as a **logical plan** (a DAG of transformations) rather than executing eagerly.\n- **Optimizing** that plan (Catalyst optimizer) before generating code (Tungsten/whole-stage codegen).\n- **Scheduling** the optimized plan as stages of parallel tasks across the cluster.\n\n## 2. Architecture\n\n```text\n               +------------------+\n               |      Driver       |   <- builds logical plan, negotiates resources,\n               |  (SparkContext)   |      schedules tasks, collects results\n               +---------+--------+\n                         |\n         +---------------+----------------+\n         |               |                |\n +-------v------+ +------v-------+ +------v-------+\n |  Executor 1   | |  Executor 2   | |  Executor N   |\n |  (JVM proc)   | |  (JVM proc)   | |  (JVM proc)   |\n |  tasks/cores  | |  tasks/cores  | |  tasks/cores  |\n |  partitions   | |  partitions   | |  partitions   |\n +---------------+ +---------------+ +---------------+\n```\n\n- The **driver** runs your code, builds the DAG, and asks the cluster manager (EMR: YARN, via Livy for this notebook's session) for executors.\n- **Executors** run **tasks** -- one task per partition per stage. Executors hold data in memory/disk (cache) and report results/status back to the driver.\n- A **job** is triggered by an **action** (e.g. `count()`, `collect()`, `write`). A job is split into **stages**, and stages are split by **shuffle boundaries**. Each stage is a set of **tasks** that can run without moving data between partitions.\n\n## 3. Transformations vs actions (laziness)\n\n- **Transformations** (`select`, `filter`, `withColumn`, `join`, `groupBy`) build the logical plan. Nothing executes yet.\n- **Actions** (`count`, `collect`, `show`, `write.save`, `toTable`) trigger execution of the plan built so far.\n\nThis laziness lets Catalyst see the *entire* plan before deciding how to execute it -- e.g. it can push a filter below a join (predicate pushdown) even though you wrote the filter after the join in your code.\n\n## 4. Narrow vs wide transformations (why shuffle matters)\n\n- **Narrow**: each output partition depends on exactly one input partition (`select`, `filter`, `withColumn`, `union`, a join against a **broadcast** table). No data movement across the network.\n- **Wide**: an output partition depends on *many* input partitions, which requires a **shuffle** -- data is repartitioned and moved across the network/disk (`groupBy`, `distinct`, `repartition`, a sort-merge join).\n\nShuffles are the single biggest cost lever in Spark: they involve disk I/O, network I/O, and serialization. Most performance tuning is really \"reduce or reshape shuffles.\"\n\n## 5. Catalyst, Tungsten, and Adaptive Query Execution (AQE)\n\n- **Catalyst** is the logical/physical query optimizer: it rewrites your DataFrame/SQL plan (predicate pushdown, column pruning, constant folding, join reordering) before picking a physical strategy (broadcast-hash-join vs sort-merge-join, etc.).\n- **Tungsten** is the execution engine: off-heap binary row format, whole-stage code generation.\n- **AQE** (on by default in modern Spark) re-optimizes the plan *during* execution using actual runtime statistics: it can coalesce many small shuffle partitions into fewer larger ones, switch a sort-merge join to a broadcast join if a table turns out to be small, and split skewed partitions.\n\n## 6. Partitioning\n\n- **In-memory partitions** control parallelism (`spark.sql.shuffle.partitions`, `repartition`, `coalesce`). Too few partitions under-utilizes the cluster; too many creates task-scheduling overhead and tiny output files.\n- **On-disk partitioning** (`partitionBy(\"event_date\")` when writing) creates a directory-per-value layout so downstream readers can skip irrelevant data (partition pruning).\n\nBelow, we run these concepts against a small synthetic clickstream dataset.")

code("schema = \"class_emr\"\nbase_path = \"s3://<your-lakehouse-bucket>/data/class-emr\"\n\ndef table(name):\n    return f\"`{schema}`.`{name}`\"\n\ndef path(*parts):\n    return base_path.rstrip(\"/\") + \"/\" + \"/\".join(p.strip(\"/\") for p in parts)\n\nfrom pyspark.sql import functions as F\n\nspark.sql(f\"CREATE DATABASE IF NOT EXISTS `{schema}` LOCATION '{path('tables')}'\")\nspark.sql(f\"USE `{schema}`\")\nprint(f\"schema={schema}, base_path={base_path}\")")

md("## Generate a small synthetic dataset\n\nWe generate deterministic data in-notebook so this class runs with no external dependency.")

code("import random\nfrom datetime import datetime, timedelta, timezone\n\nrandom.seed(7)\n\nproducts = [\n    (f\"p{i:04d}\", random.choice([\"electronics\", \"grocery\", \"home\", \"apparel\", \"beauty\"]),\n     random.choice([\"acme\", \"northstar\", \"evergreen\", \"summit\", \"nova\"]), round(random.uniform(3, 500), 2))\n    for i in range(1, 51)\n]\ncustomers = [\n    (f\"u{i:05d}\", random.choice([\"new\", \"active\", \"loyal\", \"at_risk\"]), random.choice([\"west\", \"central\", \"south\", \"east\"]))\n    for i in range(1, 201)\n]\nevents = []\nstart = datetime.now(timezone.utc) - timedelta(hours=2)\nfor i in range(200_000):\n    event_type = random.choice([\"view\", \"add_to_cart\", \"purchase\", \"search\", \"checkout\"])\n    qty = random.randint(1, 4) if event_type in (\"purchase\", \"checkout\") else None\n    price = round(random.uniform(5, 250), 2) if qty else None\n    events.append((\n        f\"evt-{i:08d}\",\n        start + timedelta(seconds=random.randint(0, 7200)),\n        random.choice(customers)[0],\n        random.choice(products)[0],\n        event_type, qty, price,\n    ))\n\nproducts_df = spark.createDataFrame(products, \"product_id string, category string, brand string, price double\")\ncustomers_df = spark.createDataFrame(customers, \"user_id string, segment string, region string\")\nevents_df = spark.createDataFrame(\n    events, \"event_id string, event_ts timestamp, user_id string, product_id string, event_type string, quantity int, price double\"\n)\n\nprint(\"Event rows:\", events_df.count())\nnum_partitions = events_df.select(F.spark_partition_id().alias(\"p\")).distinct().count()\nprint(\"Default partitions of events_df:\", num_partitions)")

md("## Laziness in action\n\nThe next cell defines transformations only. Nothing runs yet -- Spark just extends the logical plan.")

code("normalized = (\n    events_df\n    .withColumn(\"event_date\", F.to_date(\"event_ts\"))\n    .withColumn(\"event_hour\", F.date_trunc(\"hour\", F.col(\"event_ts\")))\n    .withColumn(\"quantity\", F.coalesce(F.col(\"quantity\"), F.lit(0)))\n    .withColumn(\"price\", F.coalesce(F.col(\"price\"), F.lit(0.0)))\n    .withColumn(\"gross_amount\", F.round(F.col(\"quantity\") * F.col(\"price\"), 2))\n)\nprint(type(normalized))  # still just a DataFrame wrapping a logical plan -- no job has run")

md("Calling `.count()` is an **action**: it triggers a job. Open the Spark UI (via the EMR console's \"Application user interfaces\" link, or Livy's session UI) and look at the Jobs/Stages page while this cell runs -- you'll see one job with one stage (narrow transformations only, no shuffle).")

code("print(\"Row count (triggers a job):\", normalized.count())")

md("## Narrow vs wide: broadcast join (narrow) vs groupBy (wide)\n\n`products_df` is tiny (50 rows), so Spark (via AQE, or explicitly via `F.broadcast`) sends the *whole* table to every executor instead of shuffling the large `events` table. This turns what would otherwise be a wide join into a narrow one -- no shuffle for the join itself.\n\nThe subsequent `groupBy` **is** wide: rows with the same grouping key can live on any executor, so Spark must shuffle data so each key's rows land on one executor before aggregating.")

code("enriched = normalized.join(F.broadcast(products_df), \"product_id\", \"left\")\n\nrevenue_by_category_hour = (\n    enriched\n    .filter(F.col(\"event_type\").isin(\"purchase\", \"checkout\"))\n    .groupBy(\"event_hour\", \"category\")\n    .agg(F.count(\"*\").alias(\"orders\"), F.round(F.sum(\"gross_amount\"), 2).alias(\"revenue\"))\n)\n\nrevenue_by_category_hour.explain(\"formatted\")")

md("Read the plan above bottom-up. You should see:\n\n- A `BroadcastHashJoin` (no shuffle for the join -- one side was small enough to broadcast).\n- A `HashAggregate` -> `Exchange` (shuffle) -> `HashAggregate` pair around the `groupBy`. Spark pre-aggregates partially on each executor (the first `HashAggregate`) *before* shuffling, then finishes the aggregation after the shuffle (the second `HashAggregate`) -- this is a map-side combine, the same trick MapReduce combiners use, and it drastically cuts shuffle volume.")

code("revenue_by_category_hour.orderBy(F.desc(\"revenue\")).limit(20).toPandas()")

md("## Partition count and file sizing\n\n`spark.sql.shuffle.partitions` controls how many partitions a shuffle produces. The default (200) is usually wrong for small clusters/datasets -- it creates many tiny tasks and tiny output files. AQE's `coalescePartitions` feature fixes this automatically at runtime in modern Spark, but it's important to understand the knob.")

code("print(\"Current shuffle partitions:\", spark.conf.get(\"spark.sql.shuffle.partitions\"))\nspark.conf.set(\"spark.sql.shuffle.partitions\", \"8\")\nprint(\"Set to 8 for this small demo dataset. In production, size this to (cluster core count) x 2-3, \"\n      \"or leave AQE to coalesce automatically.\")")

md("## Writing partitioned output (on-disk partitioning)\n\n`partitionBy(\"event_date\")` writes one directory per date. A downstream reader that filters on `event_date` can skip entire directories (partition pruning) without reading their data at all.")

code("(\n    normalized.join(F.broadcast(products_df), \"product_id\", \"left\")\n    .join(customers_df, \"user_id\", \"left\")\n    .write.mode(\"overwrite\")\n    .partitionBy(\"event_date\")\n    .format(\"delta\")\n    .saveAsTable(table(\"class_batch_bronze_events\"))\n)\n\nspark.sql(f\"DESCRIBE DETAIL {table('class_batch_bronze_events')}\").toPandas()")

md("## Common batch performance problems (talking points)\n\n1. **Too many small files** -- usually caused by over-partitioning on write or many small streaming micro-batches. Fix with `OPTIMIZE` (Delta) or by reducing output partition count.\n2. **Data skew** -- one join/grouping key has far more rows than others, so one task takes far longer than the rest. AQE's skew join optimization splits the largest partitions automatically; salting keys is the manual fix when AQE isn't enough.\n3. **Wrong join strategy** -- broadcasting a table that's actually large causes executor OOMs; failing to broadcast a genuinely small table causes an unnecessary shuffle. Check `explain()` to confirm.\n4. **Repeated scans** -- reading the same source multiple times instead of caching an intermediate result that's reused. Cache deliberately, and `unpersist()` when done.\n5. **Missing predicate/column pushdown** -- reading Parquet/Delta with a `filter` before a `select` lets Spark skip files/row-groups and unused columns entirely at the source. `explain()` shows `PushedFilters`.\n\n## What's next\n\nBatch processing assumes the data is already fully available. `02_spark_structured_streaming.ipynb` covers what changes when data arrives continuously and you cannot wait for \"all of it.\"")

Port of `class/02_spark_structured_streaming.py`. Note the original's `foreachBatch`/MERGE section (Step 4) already uses the "materialize a stream, then run `spark.sql(\"MERGE INTO ...\")`" pattern — no `DeltaTable` Python API to remove here, unlike `class/04`:

```
md("# Class 2 — Spark Structured Streaming (EMR)\n\nThis notebook explains how Spark processes **unbounded** data -- streams that never \"finish\" -- and how that changes the programming model, correctness guarantees, and operational concerns compared to batch.\n\n## 1. The core idea: \"streaming as an unbounded table\"\n\nStructured Streaming's foundational trick is to treat a stream as a table that keeps growing. You write the **same DataFrame/SQL transformations** you'd write for batch -- the engine repeatedly (a) reads new data since the last checkpoint, (b) applies the transformations incrementally, and (c) writes/updates the result to a sink.\n\n## 2. Micro-batch vs continuous processing\n\n- **Micro-batch** (the default, and what this project uses): Spark runs a small batch job every trigger interval.\n- **Continuous processing** (experimental, narrow operator support): true low-latency (~1ms) processing without discrete batches. Rarely used in production.\n\n## 3. Triggers\n\n- `trigger(processingTime=\"30 seconds\")` -- fixed-interval micro-batches; a true \"always on\" stream.\n- `trigger(availableNow=True)` -- process everything currently available then **stop**. This is what production notebooks use for scheduled/batch-like streaming runs.\n- `trigger(once=True)` -- legacy single micro-batch; superseded by `availableNow`.\n\n## 4. Output modes\n\n- **Append** -- only new result rows since the last trigger are emitted. Required for most sinks (Delta, Kafka). Works for non-aggregated data, and for aggregations *with* a watermark.\n- **Update** -- only rows whose aggregate value changed are emitted.\n- **Complete** -- the entire result table is re-emitted every trigger. Only viable for small aggregated results.\n\n## 5. Event time, watermarks, and late data\n\nTwo different clocks matter: **event time** (when the event actually happened) and **processing time** (when Spark received it). If you window by event time, Spark needs a rule for when it's safe to stop waiting for late data -- that's the **watermark**: `withWatermark(\"event_ts\", \"10 minutes\")` means \"once I've seen an event with timestamp T, assume I will never see an event more than 10 minutes older than T.\"\n\nIt is a **tradeoff knob**, not a filter: too short and legitimately late events get dropped; too long and Spark keeps more state for longer, with results lagging further behind wall-clock time.\n\n## 6. State, checkpoints, and fault tolerance\n\n- **State** -- data Spark must remember between micro-batches, stored in the executors' state store, backed by the checkpoint location.\n- **Checkpoint** -- a directory (must be durable storage -- S3, never local disk) storing source read progress, the state store, and sink commit metadata. **Never delete or share a production checkpoint** unless you intend to reset/reprocess from scratch.\n- Correctness end to end also depends on the **sink** being idempotent/transactional. Delta Lake's transactional writes plus streaming checkpoint offsets are what make Kafka -> Spark -> Delta exactly-once in practice.\n\n## 7. Stateful operations at a glance\n\n| Operation | Needs watermark? | Why |\n|---|---|---|\n| `groupBy(window(...))` aggregation | Yes | Otherwise Spark keeps every window's state forever |\n| `dropDuplicates([\"id\"])` on a stream | Yes | Otherwise Spark must remember every id ever seen |\n| Stream-stream join | Yes (both sides) | Both sides buffer unmatched rows until the watermark expires them |\n| Stream-static join | No | The static side has no state to expire |\n\nBelow, we build a small runnable streaming pipeline using Spark's `rate` source so these concepts can be observed without needing Kafka/MSK yet -- that's covered in `03_kafka_and_msk.ipynb`.")

md("Run the cell below first -- it configures Delta Lake for this notebook's Spark session.")

code("%%configure -f\n{\"conf\": {\"spark.jars.packages\": \"io.delta:delta-spark_2.12:3.1.0\", \"spark.sql.extensions\": \"io.delta.sql.DeltaSparkSessionExtension\", \"spark.sql.catalog.spark_catalog\": \"org.apache.spark.sql.delta.catalog.DeltaCatalog\"}}")

code("schema = \"class_emr\"\nbase_path = \"s3://<your-lakehouse-bucket>/data/class-emr\"\n\ndef table(name):\n    return f\"`{schema}`.`{name}`\"\n\ndef path(*parts):\n    return base_path.rstrip(\"/\") + \"/\" + \"/\".join(p.strip(\"/\") for p in parts)\n\ndef checkpoint(name):\n    return path(\"checkpoints\", name)\n\nfrom pyspark.sql import functions as F\n\nspark.sql(f\"CREATE DATABASE IF NOT EXISTS `{schema}` LOCATION '{path('tables')}'\")\nspark.sql(f\"USE `{schema}`\")\nprint(f\"schema={schema}, base_path={base_path}\")")

md("## Step 1 — A streaming source\n\n`rate` emits rows with a monotonically increasing `value` and a `timestamp`, at a controlled rate. We shape it into fake clickstream events so the mechanics look identical to a real Kafka payload.")

code("raw_stream = (\n    spark.readStream.format(\"rate\")\n    .option(\"rowsPerSecond\", 50)\n    .option(\"numPartitions\", 2)\n    .load()\n)\n\nevents_stream = raw_stream.select(\n    F.concat(F.lit(\"evt-\"), F.col(\"value\")).alias(\"event_id\"),\n    F.col(\"timestamp\").alias(\"event_ts\"),\n    F.concat(F.lit(\"u\"), F.lpad((F.col(\"value\") % 200).cast(\"string\"), 5, \"0\")).alias(\"user_id\"),\n    F.concat(F.lit(\"p\"), F.lpad(((F.col(\"value\") % 50) + 1).cast(\"string\"), 4, \"0\")).alias(\"product_id\"),\n    F.when((F.col(\"value\") % 10) == 0, \"purchase\").otherwise(\"view\").alias(\"event_type\"),\n    F.when((F.col(\"value\") % 10) == 0, 1).otherwise(0).cast(\"int\").alias(\"quantity\"),\n    F.when((F.col(\"value\") % 10) == 0, 29.99).otherwise(0.0).cast(\"double\").alias(\"price\"),\n)\n\nprint(\"Is streaming:\", events_stream.isStreaming)")

md("## Step 2 — Stateless streaming write (append mode, no aggregation)\n\nThe simplest streaming query: no state, no watermark needed. Every micro-batch is just filtered and appended.")

code("bronze_query = (\n    events_stream\n    .withColumn(\"_ingest_ts\", F.current_timestamp())\n    .writeStream\n    .format(\"delta\")\n    .option(\"checkpointLocation\", checkpoint(\"class_streaming_bronze\"))\n    .outputMode(\"append\")\n    .trigger(availableNow=True)\n    .toTable(table(\"class_streaming_bronze\"))\n)\n\nbronze_query.awaitTermination()\nprint(\"AvailableNow bronze streaming run completed\")\nspark.table(table(\"class_streaming_bronze\")).orderBy(F.desc(\"event_ts\")).limit(10).toPandas()")

md("Inspect the query's recent progress. `numInputRows`, `inputRowsPerSecond`, and `durationMs` are the metrics you'd wire into monitoring/alerting in production (see `emr-notebooks/05_observability_testing_performance.ipynb`).")

code("import json as _json\nfor p in bronze_query.recentProgress[-3:]:\n    print(_json.dumps({k: p[k] for k in (\"timestamp\", \"numInputRows\", \"inputRowsPerSecond\", \"durationMs\")}, indent=2))")

md("## Step 3 — Stateful streaming: watermark + windowed aggregation + de-duplication\n\nNow we read the bronze table *as a stream* (Delta tables can be both streaming sinks and streaming sources) and compute a windowed aggregate with a watermark, plus de-duplicate by `event_id`.")

code("bronze_stream = spark.readStream.table(table(\"class_streaming_bronze\"))\n\ndeduped = (\n    bronze_stream\n    .withWatermark(\"event_ts\", \"2 minutes\")\n    .dropDuplicates([\"event_id\"])\n)\n\ndeduped.createOrReplaceTempView(\"deduped_bronze_stream\")\n\nwindowed_revenue = spark.sql(\"\"\"\nSELECT\n  window(event_ts, '30 seconds') AS window,\n  product_id,\n  COUNT(*) AS orders,\n  ROUND(SUM(quantity * price), 2) AS revenue\nFROM deduped_bronze_stream\nWHERE event_type = 'purchase'\nGROUP BY\n  window(event_ts, '30 seconds'),\n  product_id\n\"\"\")\n\ngold_query = (\n    windowed_revenue.writeStream\n    .format(\"delta\")\n    .option(\"checkpointLocation\", checkpoint(\"class_streaming_gold_windows\"))\n    .outputMode(\"append\")\n    .trigger(availableNow=True)\n    .toTable(table(\"class_streaming_gold_windows\"))\n)\ngold_query.awaitTermination()\n\nspark.table(table(\"class_streaming_gold_windows\")).orderBy(F.desc(\"window.start\")).limit(20).toPandas()")

That's cheap and infinitely scalable, but plain Parquet/CSV/JSON files on S3 give you none of the guarantees a database gives you:\n\n- **No atomicity** -- if a job writing 500 Parquet files crashes after writing 300, readers can see a half-written, inconsistent dataset.\n- **No isolation** -- a reader running concurrently with a writer can see a mix of old and new files.\n- **No schema enforcement** -- nothing stops a bad job from writing a column with the wrong type or an extra column, silently corrupting downstream consumers.\n- **No update/delete** -- object storage is append/overwrite-oriented; there's no efficient way to update or delete a subset of rows without rewriting entire files/partitions.\n- **No versioning/audit trail** -- you can't easily ask \"what did this table look like an hour ago.\"\n\nThe **lakehouse** pattern layers a **table format** (a transaction log/metadata layer) on top of plain files in object storage, giving you database-like guarantees while keeping data lake economics. Delta Lake, Apache Iceberg, and Apache Hudi are the three major table formats; this project uses **Delta Lake**.\n\n## 2. How Delta Lake actually works\n\nA Delta table is: (a) a directory of Parquet data files, plus (b) a `_delta_log/` directory of JSON (and periodic Parquet checkpoint) files describing every change ever made to the table.\n\n```text\ns3://bucket/tables/silver_clickstream/\n├── _delta_log/\n│   ├── 00000000000000000000.json   <- version 0: CREATE TABLE + initial files\n│   ├── 00000000000000000001.json   <- version 1: added files from an append\n│   ├── 00000000000000000002.json   <- version 2: a MERGE (some files removed, new files added)\n│   └── ...\n├── part-00000-....snappy.parquet\n├── part-00001-....snappy.parquet\n└── ...\n```\n\nEach log entry is a set of **actions**: `add` a file, `remove` a file, change metadata, etc. A reader determines \"what does this table look like right now\" by replaying the log forward -- this is what gives you **snapshot isolation**.\n\nThis design is what enables: **ACID transactions**, **time travel** (`VERSION AS OF`/`TIMESTAMP AS OF`), **schema enforcement/evolution**, **MERGE (upsert)** as one atomic transaction, and **streaming source + sink from the same table**.\n\n## 3. The medallion architecture (bronze / silver / gold)\n\n```text\n  Kafka/MSK,          BRONZE                 SILVER                  GOLD\n  batch files    -->  raw, append-only, -->  cleaned, deduped,  -->  business-level\n                      schema-on-write,       validated,             aggregates,\n                      minimal transform      enriched with          dimensional models,\n                                             dimensions             ready for BI/ML\n```\n\n- **Bronze** -- as close to the source as possible, plus ingestion metadata.
